# Plugin Bug Audit — 2026-02-18

Audit of all amplifi.plugins for security, correctness, and cleanup. Suggested fixes are listed per plugin.

---

## amplifi.translate (`ac-wp-translator`)

### 1. Uninstall leaves options and transients behind

**Issue:** `uninstall.php` only drops the translations table and deletes `acwpt_settings` and `acwpt_flush_rules`. It does not remove:

- `acwpt_usage` (API usage history)
- `acwpt_strings_{language}` (one option per enabled language)
- Transients: `acwpt_models_list`, `acwpt_sitemap_xml`

**Fix:** In `plugins/ac-wp-translator/uninstall.php`, before or after dropping the table, add:

```php
delete_option( 'acwpt_usage' );
delete_transient( 'acwpt_models_list' );
delete_transient( 'acwpt_sitemap_xml' );

// Remove all string cache options (must run before deleting acwpt_settings if you need it for language list).
$wpdb->query( "DELETE FROM {$wpdb->options} WHERE option_name LIKE 'acwpt_strings_%'" ); // phpcs:ignore WordPress.DB.PreparedSQL.InterpolatedNotPrepared
```

---

### 2. Minor: Admin output escaping

**Issue:** In `class-acwpt-admin.php` around line 341, the current-month row uses `echo $is_current ? ' <em>(current)</em>' : '';`. The string is static (no user input), so risk is minimal, but for consistency and future-proofing, output can be escaped.

**Fix:** Use `echo $is_current ? ' <em>' . esc_html__( '(current)', 'ac-wp-translator' ) . '</em>' : '';` or keep as-is and document that the literal is safe.

**Severity:** Low (no user input).

## amplifi.meta (`ac-bulk-meta`)

### 1. Uninstall does not remove plugin-written post meta

**Issue:** Uninstall drops the `ac_faqs` table and several options but does not delete post meta that the plugin writes:

- `_ac_faqs_deployed`
- `_ac_jsonld` (or `_ac_jsonld_data` if used elsewhere)

**Fix:** In `plugins/ac-bulk-meta/uninstall.php`, add:

```php
// Remove plugin post meta (FAQ deploy flag, JSON-LD per post).
$wpdb->delete( $wpdb->postmeta, array( 'meta_key' => '_ac_faqs_deployed' ) );
$wpdb->delete( $wpdb->postmeta, array( 'meta_key' => '_ac_jsonld' ) );
```

Use the correct meta key(s) if the codebase uses a different name (e.g. `_ac_jsonld_data`).

---

### 2. Dark mode user meta

**Issue:** Dark mode is stored in user meta (`ac_bulk_meta_dark_mode`). Uninstall does not clean it. Optional: leave as-is (harmless) or delete for a full cleanup.

**Fix (optional):**  
`delete_metadata( 'user', 0, 'ac_bulk_meta_dark_mode', '', true );` to delete all keys with that meta key.

## amplifi.magic (`ac-magic-links`)

### 1. CSRF: Create/revoke token forms lack nonces

**Issue:** The “Create Token” and “Revoke” actions are handled in `ocml_admin_page()` based only on `$_POST` and `current_user_can('manage_options')`. There is no `wp_nonce_field` / `check_admin_referer`, so actions are vulnerable to CSRF (e.g. an admin could be tricked into creating or revoking tokens via a cross-site form POST).

**Fix:**

- In `ocml_admin_page()`, before handling create/revoke, verify nonce, e.g.:

  ```php
  if ( isset( $_POST['ocml_create_token'] ) && isset( $_POST['ocml_post_id'] ) && current_user_can( 'manage_options' ) ) {
      if ( ! isset( $_POST['ocml_nonce'] ) || ! wp_verify_nonce( $_POST['ocml_nonce'], 'ocml_admin' ) ) {
          wp_die( 'Security check failed.' );
      }
      // ... existing create logic
  }
  ```

  Do the same for the revoke block (use the same action name `ocml_admin` or a separate one like `ocml_revoke`).

- In both forms (create token and revoke), add:

  ```php
  wp_nonce_field( 'ocml_admin', 'ocml_nonce' );
  ```

**Severity:** Medium (admin-only but CSRF is a best-practice fix).

---

### 2. Permalink output escaping

**Issue:** Around line 90, permalinks are echoed without escaping:

```php
echo 'Permalink: <a href="' . get_permalink($page->ID) . '" target="_blank">' . get_permalink($page->ID) . '</a>';
```

`get_permalink()` is generally safe, but for attributes and display, URLs should be escaped.

**Fix:**

```php
$permalink = get_permalink( $page->ID );
echo 'Permalink: <a href="' . esc_url( $permalink ) . '" target="_blank">' . esc_html( $permalink ) . '</a>';
```

## amplifi.lockcache (`ac-static-cache`)

### 1. Preload All does not actually populate cache

**Issue:** “Preload All” calls `wp_remote_get( $url )` for each password-protected post. Those requests do not send the post password cookie, so the server returns the password form. The plugin only caches when the content is unlocked (no password form in the HTML). As a result, Preload All does not create or update cache files.

**Fix (options):**

- **Option A (recommended):** Document in the UI that “Preload All” only warms cache for posts that have already been unlocked at least once (e.g. by a visitor with the cookie), and that it will not unlock posts by itself.
- **Option B:** Implement preload by triggering internal requests that set the password cookie (e.g. using the same cookie hashing as the magic-links plugin, if a token exists), or by using an internal “preload” key stored in options. This is more complex and may require storing a preload password or integrating with amplifi.magic.

---

### 2. Log file read can be large

**Issue:** `read_log_file_newest_first()` uses `file()` to load the entire log into memory. On very busy sites the log could grow large.

**Fix:** For large files, read the last N bytes or last N lines (e.g. with `SplFileObject` or reading in chunks from the end). For typical usage, current behavior is acceptable; add a note in the admin that the log is “newest first” and may be truncated or rotated if it gets very large.

**Severity:** Low.

---

### 3. `$_REQUEST` in S&F detection

**Issue:** `is_searchandfilter_request()` uses `$_REQUEST['sfid']`, `$_REQUEST['sf_data']`, `$_REQUEST['sf_action']`. Prefer `$_GET` if the plugin only uses GET for those params, to avoid ambiguity with POST.

**Fix:** Use `$_GET` if Search & Filter Pro sends these in the query string; otherwise leave as-is and document.

**Severity:** Low.
